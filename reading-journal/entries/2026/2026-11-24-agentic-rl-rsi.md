# Reading guide

本文把 Agentic RL 放在 RLHF→RLVR 的后训练演进线上：关键变化不是换一个优化器，而是把策略置入多轮、带工具且状态会变化的环境，使 rollout、奖励、功劳分配与上下文管理共同成为训练系统的一部分。

一句话主旨：Agentic RL 正在把模型从“生成正确答案”推向“完成长程任务”，但它自动化的仍主要是权重更新，距离递归自我改进（RSI）的完整研究—训练闭环很远。

建议先读第二至四节建立概念和机制，再用第五节观察不同团队如何选择数据、环境与奖励，最后读第六至八节检查 RSI 推论和证据缺口。最可靠的部分是对已公开论文机制及工程瓶颈的综合；厂商 benchmark、成本折算、2026 年新工作和“70% 性能来自 harness”等主张需要按各自实验协议独立核验。

阅读时持续追问：当任务分布、环境和奖励仍由人定义时，模型提升究竟来自可迁移的决策能力，还是来自对特定验证器与训练环境的适配？

## 术语史与能力边界

<!-- x-read-anchor {"heading":"二、先把概念对齐，RLHF、RLVR 和 agentic RL","passage":"一句话对齐：RLHF 学的是怎么说人话，RLVR 学的是把题做对，agentic RL 学的是把事干完。"} -->

这条三段式适合作为工程直觉，但不应读成互斥分类。RLHF 可以包含可验证信号，RLVR 也可能用于多轮轨迹；“agentic RL”更像训练任务与环境的属性，而不是与 RLHF、RLVR 同层级的单一算法。Tülu 3 对可验证奖励的系统化使用很有代表性，但“RLVR”一词的首创归属应谨慎表述；更稳妥的判断依据是奖励能否由确定性或可审计的 verifier 计算。

## 长程任务的乘法难度

<!-- x-read-anchor {"heading":"三、为什么单轮 RL 不够用","passage":"这些麻烦凑在一起，就凑出了 agentic RL 要解决的几件事：轨迹怎么收（rollout）、奖励怎么给（reward）、功劳怎么分（credit assignment）、上下文怎么管（context management）。第四节按这个"} -->

四个问题并非独立相加。轨迹越长，成功样本越少，结果奖励的方差越大；为补足信号而引入过程奖励，又会扩大 judge 偏差与 reward hacking 的攻击面。环境非平稳还会让旧策略采得的轨迹与当前策略发生分布偏移，因此系统设计、统计效率和奖励可信度必须一起评估。

## 吞吐不等于样本效率

<!-- x-read-anchor {"heading":"4.1 rollout：把轨迹收上来","passage":"工程上的主流解法是异步化：训练 GPU 和推理 GPU 分开，两边各自跑，中间用一个缓冲区接轨迹。同步模式下训练等 rollout 收满，rollout 又等训练更新完才能继续，两边轮流空转。异步模式下两边都不等，代价是 rollout 收"} -->

异步 rollout 优化的是墙钟时间和硬件利用率，但 stale trajectories 会使数据偏离当前策略。评价框架时至少要同时看：达到同一任务成功率的 GPU-hours、生成 token 数、策略版本延迟和最终稳定性。仅报告吞吐倍数，无法证明总体训练更省或所得策略更好。

## 奖励的真正接口是可审计性

<!-- x-read-anchor {"heading":"4.2 奖励：最花人工的部分","passage":"我的判断：奖励这一块，短期看规则工程，中期看过程奖励模型，长期我还没看清楚。哪家先把新任务域的奖励成本降下来，哪家就能把 RL 往更多业务上推，这是竞争的焦点之一。"} -->

规则、过程奖励模型和 self-critique 的共同难点不是“能否输出一个分数”，而是分数能否追溯到任务规范，并在策略变强后仍保持校准。面向真实业务，应保留独立 holdout verifier、失败类型审计和对抗性轨迹测试；否则优化器很可能先学会利用评分器，再学会完成任务。

## 功劳分配需要反事实证据

<!-- x-read-anchor {"heading":"4.3 算法：从 PPO 到 GRPO，再到多轮功劳分配","passage":"这里要多说一句：GiGPO 和 ARPO 的目标函数我只看了直觉层面的解释，成立条件和收敛性没有从数学上确认，论文实验也是各跑各的基准，横向没有统一对照，哪个方法真正占优我下不了结论。第八节还会再提这个坑。"} -->

将 episode advantage 切到轮级或状态组，只是构造了更细的估计量；它是否正确归因，仍取决于状态可比性、后续策略与环境随机性。更强的验证应包含动作替换或前缀干预：固定轨迹前缀，只改变目标动作并重复 rollout，观察最终成功率差异。没有这类反事实测试，步级 advantage 可能只是相关性代理。

## 把记忆当动作会新增训练目标

<!-- x-read-anchor {"heading":"4.4 上下文：长轨迹塞不进训练窗口","passage":"2025 年底开始出现更成熟的做法：把整理上下文本身当成动作。MemAct（Memory as Action，arXiv:2510.12635）把模型对上下文的压缩和存取决策建模成动作序列，端到端进 RL，让模型自己学出该记什么、什么时候取"} -->

主动压缩并不免费：记忆动作需要额外 credit assignment，而且压缩错误可能在许多轮之后才暴露。除了任务成功率，还应测量关键信息召回、错误恢复、压缩率和对提示注入内容的保留倾向。长上下文、外部记忆与 learned compression 是可组合方案，不是单线替代关系。

## 成本口径不能横向直接相除

<!-- x-read-anchor {"heading":"4.5 训练框架和成本账","passage":"售前的角度多说一句：客户如果问自己训 agentic RL 要花多少钱，按上面的量级加上环境搭建和人力，第一年数百万人民币是要准备的，而且大头不在 GPU，在环境搭建和奖励规则这两块人工上。这个判断来自公开材料加个人经验，仅供参考，真要立项"} -->

GPU 型号、有效利用率、轨迹长度、失败重试、环境并发和是否计入 SFT/数据生成都会改变“GPU 小时”的含义。文中的美元折算可用于数量级直觉，不适合成为项目报价。更可迁移的预算单位是“每个通过独立评测的成功轨迹成本”，并将环境开发、验证器维护和人工审计单列。

## 表格是厂商口径索引，不是排行榜

<!-- x-read-anchor {"heading":"五、各家在怎么做","passage":"五家放在一起看，共性比差异显眼：奖励的地基都是可验证信号，差异主要在数据怎么合成、环境怎么搭。GLM 重流程显式分阶段，Kimi 重数据工程，DeepSeek 重算法极简，Qwen3 的 Coder 系重测试用例自动生成，MiniMax 切"} -->

SWE-bench、TAU-bench、MATH-500 与动作链长度测量的是不同能力，且提交次数、工具配置、测试时预算和数据污染控制可能不同。这里适合比较训练配方的公开侧重点，不适合用单列数字推导模型优劣。复核时应回到各自技术报告和 benchmark 的 evaluation protocol。

## RSI 不只看自动化环节数量

<!-- x-read-anchor {"heading":"六、agentic RL 和 RSI 是一回事吗","passage":"我的判断：agentic RL 现在是自动训练，还不是自我训练。中间差的主要是循环里那五个环节的自动化程度，算法反而不是主要矛盾。哪个环节先被自动化，哪个环节就会先出现新一轮 reward hacking，模型钻自己的空子比钻环境的空子容易"} -->

“六环节全部自动化”是有用的系统分解，但 RSI 还要求改进具有递归性、跨代保持、可验证净收益，并且改进机制本身能扩展。自动出题或修改 harness 属于局部自举；若任务分布、验证器或硬件预算仍固定，它们不必然形成开放式能力增长。判断 RSI 应看闭环的因果自主性和跨迭代增益，而不只是自动化勾选项。

## 真实 harness 既降分布差，也扩大风险面

<!-- x-read-anchor {"heading":"七、回到 Agent = Model × Harness","passage":"最有意思的合流点是 Agent Lightning 的思路：把 RL 的 rollout 直接放在 Claude Code、Codex 这类真实 harness 里跑，训练时见到的环境就是上线后运行的环境，只改 baseurl 就能接入。等"} -->

在部署 harness 中采样可减少训练—上线接口差异，但也会把工具权限、外部服务波动、隐私数据和不可逆副作用带进训练。可行的工程边界通常是可重放沙箱、最小权限凭据、幂等工具、轨迹脱敏和独立验收器；“接入真实 harness”本身不保证数据安全或策略可迁移。
